# job-star 设计文档：Boss 直聘岗位匹配与沟通助手

日期：2026-09-14
状态：设计已确认，待写实现计划

## 1. 问题

求职者手上有一个成熟的素材库（`简历主库-MASTER.md` 70KB、10 余个成型简历版本、面试问答库、项目案例）。在 Boss 直聘上找工作的实际瓶颈不是写简历，而是：

1. 逐个读 JD 判断是否值得投，重复且耗神
2. 判断标准不稳定，同类岗位今天投明天不投
3. 打招呼话术每次重写
4. 投过什么版本、当时为什么觉得匹配，事后完全回忆不出来

本项目为上述流程建立一条可复现、可留痕、可校准的流水线。

## 2. 范围

### 第一版做

Boss 直聘单平台的**流 A**：岗位采集 → 硬条件门禁 → LLM 维度打分 → 打招呼话术草稿 → 待确认队列 → 人工确认 → 执行发送 → 留痕。

### 第一版不做

| 不做的 | 理由 |
|---|---|
| 猎聘 | DOM 与风控机制与 Boss 完全不同，同时做调试成本翻三倍；岗位重合度高 |
| 流 B：HR 对话回路 | 流 A 未跑通前没有 HR 对话可处理 |
| 流 C：定制简历生成与投递 | 同上，且依赖流 B 的「要简历」意图判定 |
| 向量检索 / RAG | 见 §5.2，当前数据量下是负优化 |
| 长期对话记忆层 | 属于想象中的难点，并行对话 5-10 个时全量注入即可 |

流 B、流 C 的设计要点记录在 §9，供后续版本参考，但不在本次实现计划内。

### 明确的非目标

本系统**不做全自动投递**。所有对外发送动作必须经过人工在面板上逐条确认。

### 3.1 核心设计原则

**决策器与执行器彻底分离。** 决策器是纯函数：输入岗位 + 能力卡片，输出「建议动作」，不持有浏览器句柄。执行器只消费队列中状态为 `approved` 的动作，不做任何判断。

这带来两个关键性质：决策逻辑可以离线回放历史岗位来调权重和 prompt，而不可能误发消息；执行器可以独立做节流和风控，不受决策逻辑变更影响。

**单一待确认队列。** 未来的打招呼、回复、投简历三类动作共用同一张 `actions` 表、同一个确认界面。第一版只有 `send_greeting` 一种类型，但表结构按多类型设计。

**打分结果连同证据落库。** 分数不是一个数字，而是 `{维度: {分数, 引用的卡片 id, 命中理由, 缺口}}`。阈值调不准时可以定位到是哪个维度虚高，而不必重跑。

## 4. 组件

每个组件有明确的输入、输出和依赖，可独立测试。

### 4.1 采集器 `collector`

- **职责**：从 Boss 直聘抓取岗位列表与详情，写入 `jobs` 表
- **输入**：搜索条件（关键词、城市、薪资范围）
- **输出**：`jobs` 记录（原始 JD 文本 + 平台元数据）
- **依赖**：browser-harness（CDP 复用本地 Chrome 登录态）
- **两阶段抓取**：先抓列表页摘要，经硬门禁筛选后，只对幸存岗位抓详情页。将详情页请求量压到约 1/5，这既是性能优化也是风控措施。
- **去重**：以平台 `job_id` 为唯一键，已存在则跳过

### 4.2 归一化器 `normalizer`

- **职责**：将 JD 自由文本抽取为结构化 `JobRequirements`
- **输出字段**：城市、学历要求、经验年限、薪资区间、技能要求列表、行业、公司规模、岗位类别
- **实现**：LLM 单次调用，输出 JSON schema 约束的结构

### 4.3 硬门禁 `gate`

- **职责**：纯规则过滤，不调用 LLM
- **规则**（全部可在面板设置中配置）：城市白名单、最低薪资、学历是否卡死、经验年限区间、公司黑名单
- **输出**：通过 / 拒绝 + 拒绝原因（落库，便于事后检查门禁是否过严）

### 4.4 能力卡片库 `evidence_store`

将 `简历主库-MASTER.md` 离线提炼为结构化能力卡片。卡片格式：

```yaml
- id: cap-rag-telecom
  能力: RAG / 文档智能问答
  同义表述: [检索增强, 知识库问答, 文档智能, 向量检索]
  证据强度: 强          # 强=能讲30分钟 / 中=能讲5分钟 / 弱=仅接触
  项目: 电信扫描件 OCR + RAG
  可量化: [准确率, 文档量, 演示层级]
  可讲深度: OCR 预处理、分块策略、召回优化、领导演示答疑
  关联简历版本: [后端AI版, 财务AI专家版, 道富AI应用版]
```

**「证据强度」字段是本系统防止简历吹牛的唯一防线**：弱证据卡片不得作为某维度的主要匹配依据，只能作为加分项。打分器对此有硬性约束。

生成流程：agent 跑一遍 MASTER.md 产出初稿（预计 30-50 张卡片），**由本人逐张校对「证据强度」列**，约需一小时。这是一次性投入。

检索接口按 Protocol 定义，第一版实现为全量返回：

```python
class EvidenceStore(Protocol):
    def retrieve(self, jd: JobRequirements) -> list[CapabilityCard]: ...

class FullDumpStore:   # 第一版：忽略 jd，返回全部卡片
```

### 4.5 打分器 `scorer`

- **输入**：`JobRequirements` + 全部能力卡片
- **输出**：各维度分数 + 引用卡片 id + 命中理由 + 缺口说明 + 加权总分
- **维度**（权重可在面板配置）：技能匹配、行业匹配、岗位职责匹配、经验年限、加分项
- **约束**：每个维度的分数必须附带至少一张卡片 id 作为证据，否则该维度记 0 分
- **纯函数**：不写库、不碰浏览器，可对历史岗位批量回放

### 4.6 话术生成器 `pitch_writer`

- **输入**：`JobRequirements` + 打分结果（含命中的卡片）
- **输出**：打招呼话术草稿
- **要求**：引用 JD 中的具体关键词作为钩子，避免模板化开头（前 20 字相似度是风控信号之一）

### 4.7 待确认队列 `actions`

状态机：`pending → approved → sent`，或 `pending → skipped`，或 `approved → failed`。

第一版动作类型只有 `send_greeting`。表结构预留 `type` 字段以容纳未来的 `send_reply`、`send_resume`。

### 4.8 执行器 `executor`

- **只消费 `approved` 状态的动作**
- **每日配额**：从 `settings` 表读取，**可在面板中设置**（不硬编码）。默认值 25，作为防止一次性批准过多的闸门
- **节流**：动作之间插入随机延迟，分布模拟人类长尾而非均匀间隔
- **失败处理**：写入失败原因，置为 `failed`，不自动重试（人工在面板决定是否重试）

### 4.9 Web 面板 `panel`

单页应用，四个视图：

1. **待确认队列**：岗位摘要 + 总分 + 话术草稿，支持确认 / 跳过 / 改写后确认
2. **分数拆解**：点开某岗位，看各维度分数、引用的卡片、缺口
3. **标注**：冷启动期使用，键盘 `y` / `n` 快速翻条目标注「会投 / 不会投」
4. **设置**：每日打招呼上限、硬门禁规则、维度权重、分数阈值

## 5. 关键技术决策

### 5.1 为什么打分要拆维度 + 硬门禁前置

直接让 LLM 对整个 JD 输出一个百分数，同一岗位多次评分会漂移，阈值失去意义。硬门禁先用规则刷掉 60-80% 明显不合的岗位（不花 token），剩余岗位再拆维度打分，每个维度必须附证据。分数因此可解释、可定位。

### 5.2 为什么第一版不用向量检索

向量 RAG 解决的是「上下文装不下」，当前问题是「语义对不齐」，两者不同。30-50 张卡片、摘要总量 3-5KB，全量注入使模型能通盘对照。引入 top-k 召回反而新增一个失败模式：JD 写「熟悉 Agent 框架」，向量检索可能因措辞差异召回不到「LangGraph 多轮编排」卡片，该维度被误判为不匹配；而全量注入时模型直接能看见。

提升对齐质量的正确做法是把卡片的「同义表述」字段写全，不是换检索方式。

**何时重新评估**：卡片数超过 200 张，或摘要总量超过 30KB，或开始纳入面试问答库与历史对话记录。届时实现 `VectorStore` 替换 `FullDumpStore`，打分器无需改动。

### 5.3 阈值的冷启动流程

**第一版交付时不设阈值，一条消息都不发。** 流程：

1. 第一周：所有岗位正常采集打分，全部只进标注视图，不进待确认队列
2. 人工标注 30-50 个岗位「会投 / 不会投」
3. 用标注反推阈值：看「会投」组的分数分布落在哪个区间
4. 同时检查维度权重：若「会投」组中大量岗位被某维度显著拉低，说明该维度权重过高

**这批标注同时是回归测试集。** 此后任何 prompt 或权重改动，重跑这批岗位对照标注，一致率上升才允许合入。这是防止系统「越调越差」的唯一机制。

### 5.4 账号风险控制

Boss 风控识别的是行为分布而非脚本本身。已采取的措施：

- 半自动形态：发送节奏由人工点击决定，天然是人类分布
- 两阶段抓取：详情页请求量压至 1/5
- 可配置的每日配额闸门
- 动作间随机延迟，长尾分布
- 话术要求引用 JD 具体关键词，避免固定开头

**已知未验证风险**：Boss web 端登录态的有效期。扫码登录频率可能高于预期，需实测。若频繁失效，需在面板中加入登录态健康检查与重新扫码提示。

## 6. 数据模型

```
jobs            岗位原始数据。platform, job_id(唯一), title, company,
                raw_jd, city, salary_raw, collected_at, detail_fetched

requirements    归一化结果。job_id, city, degree, years, salary_min/max,
                skills(json), industry, category

gate_results    门禁结果。job_id, passed, reject_reason

scores          打分结果。job_id, total, dimensions(json: 每维度分数/
                引用卡片id/理由/缺口), scored_at, scorer_version

actions         待确认动作。id, type, job_id, payload(话术等),
                status(pending/approved/skipped/sent/failed),
                created_at, decided_at, sent_at, error

applications    投递台账。job_id, action_id, hr_name, greeting_text,
                score_snapshot(json), sent_at
                (第一版记录打招呼；流 C 上线后补 resume_version_hash)

labels          人工标注。job_id, would_apply(bool), labeled_at

settings        面板可配置项。key, value
                含: daily_greeting_limit, score_threshold,
                    gate_rules, dimension_weights
```

`scorer_version` 字段用于区分不同 prompt/权重版本产生的分数，支持回归对比。

## 7. 错误处理

| 场景 | 处理 |
|---|---|
| 登录态失效 | 采集中止，面板顶部横幅提示重新扫码，不静默失败 |
| 页面结构变更导致抓取失败 | 记录失败岗位与原始 HTML 片段，继续处理其余岗位，面板汇总提示 |
| LLM 返回不合 schema | 重试一次；仍失败则该岗位标记 `scoring_failed`，进入面板待人工处理，不猜测分数 |
| 发送失败 | 动作置 `failed` 并记录原因，不自动重试 |
| 触达每日配额 | 执行器停止消费队列，面板显示剩余额度与重置时间 |
| 某维度无证据卡片 | 该维度记 0 分，不允许 LLM 无引用给分 |

## 8. 测试策略

- **纯函数层**（归一化、门禁、打分、话术生成）：以固化的 JD 样本为输入做快照测试，不依赖网络与浏览器
- **回归测试集**：§5.3 产出的 30-50 条人工标注，作为打分器的黄金标准，任何 prompt/权重改动需对照跑
- **执行器**：mock 浏览器层，验证配额、状态机、延迟分布
- **采集器**：对固化的 HTML 样本做解析测试；活体抓取仅做冒烟检查

## 9. 后续版本要点（不在本次范围）

**流 B：HR 对话回路。** 轮询未读消息 → 抓对话上下文 → 意图分类（要简历 / 问具体问题 / 约面试 / 婉拒）→ 分流。约面试类不自动回复，顶到面板最前；婉拒类自动归档。对话上下文第一版全量注入，不建记忆层。

**流 C：定制简历生成。** 采「只改头部、主体冻结」策略：从现有 10 余个版本中按岗位画像选基础版，仅重写「个人简介 / 核心优势 / 项目排序」。技术方案为模板占位符法——把 2-3 个常投版本做成携带格式的模板，正文段落替换为 `{{SUMMARY}}` 等占位符，生成时只做文本替换不碰样式，规避 python-docx 丢失 run 级格式的问题。**必须加验证闸门**：生成后转 PDF 比对页数，与基础版不一致则打回。投递后按内容 hash 冻结快照存 `versions/<hash>.docx`，台账记录 hash + 当次分数拆解，便于面试前调取「当时投的原件 + 当时为什么觉得匹配」。

## 10. 技术栈

Python + SQLite + FastAPI + 单页 HTML 面板；浏览器层复用已有的 browser-harness（CDP 连接本地 Chrome，复用登录态）。
